Quarkus完全指南：从JVM到原生镜像

发表于2026-11-19|更新于2026-11-19|代码

为什么有 Quarkus

Java 在容器时代有两个致命短板：启动慢（JVM 预热 + 类加载，秒级起步）和内存大（随便一个 SpringBoot 空跑就是 300MB+）。在 K8s 按内存计费、Serverless 要求毫秒冷启动的场景里，这两个短板是要真金白银付费的。

Quarkus 是 Red Hat 主导的”云原生 Java”框架，思路是把尽可能多的工作从运行时挪到构建期：依赖注入在编译时织好、反射元数据提前收集、配置在构建时固化。最终产物可以两种形态运行：

  • JVM 模式：还是 java -jar，但因为构建期做完了初始化，启动和内存都比 SpringBoot 好
  • Native 模式：再用 GraalVM 把整个应用 AOT 编译成机器码 exe，彻底没有 JVM——毫秒启动、几十 MB 内存

本文从建项目到原生编译到压测对比走一遍完整流程，我是Windows环境哦。

建项目

IDE 配置与运行（以 VSCode 为例）

dev 模式

上面那个 Debug Quarkus 按钮跑的就是 dev 模式（本质是 ./mvnw quarkus:dev），也可以在 VSCode 集成终端里手动跑：

dev 模式的价值：

  • 保存即生效：改代码不用重启，live coding 后台编译+热替换，比 SpringBoot devtools 的重启式热加载快得多

基础用法

Quarkus 3.x 用的是 Jakarta REST（原 JAX-RS） 标准 + CDI 依赖注入，写法跟 Spring MVC 几乎同构，Spring 背景的基本零成本迁移。

本章用到的扩展

先把依赖贴全——下面每个小节用到什么都会标注，pom 里对应这几项（版本号不用写，BOM 统一管）：

用 code.quarkus.io 或 CLI 勾选扩展建项目的话这些会自动配好，这里贴出来是让你知道每个功能对应哪个 artifactId。

REST 接口：@Path + @GET

扩展：quarkus-rest

对照 Spring：@Path ≈ @RequestMapping（类+方法上都能加，拼接成完整路径）、@GET/@POST/@PUT/@DELETE ≈ @GetMapping 等。类上的 @Produces/@Consumes 声明整个类的默认媒体类型，方法级可以覆盖。

参数绑定

其他绑定注解：@HeaderParam（请求头）、@CookieParam（cookie）、@MatrixParam（路径里的 ;k=v）。参数多了还可以用 @BeanParam 打包成一个对象：

参数类型自动转换：String、数字、boolean、LocalDate/LocalDateTime（ISO 格式）、枚举、Optional<T> 都行，不用手写转换器。

返回值与序列化

扩展：quarkus-rest-jackson（quarkus-rest 只带基本文本能力，JSON 序列化靠它）

  • POJO/Map/List：加 quarkus-rest-jackson 扩展后自动 JSON 序列化，@Produces 默认 application/json，基本不用写
  • **Response**：要控制状态码/header 时用 Response.ok(entity).header("X-Tag", "v1").build()、Response.status(404).build()，等价于 Spring 的 ResponseEntity
  • **Uni<T> / Multi<T>**：响应式返回，见进阶篇
  • 文本：直接返回 String，@Produces(MediaType.TEXT_PLAIN)

依赖注入：CDI

扩展：quarkus-arc（ArC 是 Quarkus 的 CDI 实现，一般随 quarkus-rest 传递进来）

进阶用法

响应式：Uni 与 Multi

扩展：Mutiny 内置，不用加依赖

Quarkus 的响应式类型是 Mutiny 的 Uni（0 或 1 个结果，≈ Mono）和 Multi（流，≈ Flux）。方法返回 Uni 就是非阻塞接口——请求挂在 Vert.x event loop 上，不占用 worker 线程：

Multi 配合 @Produces(MediaType.SERVER_SENT_EVENTS) 就是现成的 SSE 流式推送。

阻塞 vs 非阻塞：线程模型

Quarkus REST 默认在 event loop 线程上跑——你的代码里写阻塞调用（JDBC、sleep）会卡住整个 loop。两种解法：

  • **@Blocking**：标在方法/类上，请求转给 worker 线程池处理（传统写法的数据库操作必须加）
  • @RunOnVirtualThread：JDK 21+ 的福音，标上后跑在虚拟线程上——写同步代码拿异步性能，Java 系里 Quarkus 对虚拟线程的支持是最顺手的

非阻塞路线（Uni）才是性能天花板，但 @RunOnVirtualThread 是心智成本和收益的最优平衡点。

异常处理：ExceptionMapper

实现 ExceptionMapper + @Provider，等价于 Spring 的 @ControllerAdvice。不想写 mapper 的话直接抛 WebApplicationException(消息, 状态码) 也行，校验错误框架自己会返回 400。

扩展：quarkus-rest-client + quarkus-rest-client-jackson（JSON 响应）

测试：@QuarkusTest

扩展：quarkus-junit5 + rest-assured（都是 test scope）

@QuarkusTest + RestAssured 是官方组合，测试跑的是完整应用但启动极快。配套还有 @TestHTTPEndpoint（自动定位路径）、@QuarkusTestResource（测数据库时自动拉 Testcontainers）。

JVM 模式实测

先放个基准（hey -z 10s，本地回环）：

指标 数值
启动时间 ~434 ms
JSON QPS 195,546
fib(35) QPS 394
压测后 RSS ~299 MB

对比 SpringBoot 同接口：48k QPS / 337MB——快 4 倍、省 11% 内存，这还只是 JVM 模式。

Native 模式：GraalVM 原生编译

工具链（Windows 的坑全在这）

需要三样：

  1. MSVC：装 Visual Studio Build Tools（我用的是 vcvars64.bat）
  2. GraalVM：注意版本对应——Quarkus 3.40 要 GraalVM 25，装 17/21 的老版本会直接被拒
  3. Native Image 组件（Oracle 版自带；CE 版 gu install native-image）

GraalVM 分 CE（社区版，免费）和 EE（Oracle 版，GFTC 许可开发免费）。EE 编译产物明显更快，后面数据会体现。

编译

产物：target/xxx-runner.exe，约 40MB（对比 Go 同功能 exe 9.8MB）。

Native 实测

指标 Native CE Native EE
冷启动 55 ms 55 ms
空闲内存 27 MB 27 MB
JSON QPS 174,139 179,848
fib(35) QPS 239 348

有意思的点：**EE 比 CE 快 46%**——因为 Oracle 版默认就启用了 ML-inferred PGO（内置画像引导优化）。这也引出了下一个话题。

PGO：用真实流量画像重新编译

PGO（Profile-Guided Optimization）流程：先编插桩版 → 跑真实流量采样 → 拿画像文件 default.iprof 重新编译。

踩坑：native-image 只在自己的工作目录找 default.iprof，bat 传路径参数容易被吞，最稳的办法是从构建日志里抠出完整 native-image 命令行手动执行。

PGO 结果

接口 EE（ML画像） EE + 采样PGO
JSON QPS 179,848 202,489（+12.6%）
fib(35) QPS 348 249（倒退了）

PGO 的坑：画像是按执行频率加权的。采样时 JSON 接口跑了 150 万次、fib 只有几千次，编译器把优化预算全给了 JSON 路径，CPU 密集路径反而被降级。真实项目要采和业务流量分布一致的画像，否则优化会”偏科”。

资源占用

框架 内存 启动 产物体积
Go 18 MB 毫秒 9.8 MB
Quarkus Native 27~50 MB 55 ms ~40 MB
Quarkus JVM 299 MB 434 ms 数 MB

两个反直觉的结论：

  1. CPU 密集计算 native 打不过 JVM：JIT 有运行时 profiling 可以激进内联，AOT 拿不到这些信息。fib 场景 JVM 比 native 快 13~60%。
  2. Go 的 fib 反而最慢梯队：递归斐波那契考验的是函数调用开销，Go 的调用约定在这不占优，250 QPS 甚至打不过 SpringBoot。

Kotlin 支持

Quarkus 官方支持 Kotlin，跑分和 Java 几乎一样（189k vs 195k QPS，噪声范围）——同字节码同 JIT。差异全在开发体验：data class、空安全、协程（suspend fun 可直接写异步接口）。踩过的坑是版本对齐：Kotlin 编译器版本要跟 Quarkus 带的 coroutines/reflect 对齐，pom 里显式指定 kotlin-stdlib 版本，别指望 BOM。

选型建议

场景 选什么
常驻大服务、追求吞吐天花板 Quarkus JVM 模式（JIT 上限最高）
Serverless / 高密度容器 / 弹性伸缩 Quarkus Native（55ms 启动 + 27MB 空闲）
极简依赖、小团队、基础设施无关 Go（9.8MB 单文件还是香）
国内生态、Spring 平替 Solon 可以看看
现成 SpringBoot 没必要为性能重写

Native 的代价也要说清：编译 46 秒 vs jar 打包几秒、反射/动态代理/资源加载要额外配置 reachability metadata、调试链路变长。Quarkus 的主流扩展都内置了 native 元数据，但用了冷门库就要自己填坑。
